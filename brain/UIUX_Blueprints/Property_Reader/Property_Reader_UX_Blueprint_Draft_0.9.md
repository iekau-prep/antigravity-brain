## 1. Purpose
気になる物件を手軽に登録・保存し、内見前後の判断を本人の言葉や任意タグで記録し、あとから再開・比較・振り返りができる。サービスは購入の良否を判定しない。各入口から来たユーザーが、次に何をすればよいか迷わない。

## 2. Mobile Journey：基本4画面
### A｜物件を追加する
- 物件掲載URLを主入口とする。URLがない、またはAIが読めない場合も画像・PDF・手入力で続行可能。
- 必要ならシステム提供プロンプトをコピーしてChatGPT/Gemini等へ渡す。ユーザー自身がURL・資料・テキストを提供する。
- AI出力には、コピー・家買う予備校への復帰方法、および同じ入力セッションに戻るリンクを含める案。リンクだけで物件データが自動連携されるとは扱わない。
- モバイルChromeで別タブ／外部AIアプリへ移動しても、下書き・現在位置を保持。元のタブに戻れない場合も同じ入力対象を再開可能にする。復帰用URLに個人情報やAI成果物全体を含めない。
### B｜物件情報を確認する
- 比較用の基本9項目を優先表示：価格、専有面積、築年・築年数、管理費、修繕積立金、最寄り駅、徒歩分数、間取り、総戸数。
- そのほか資料に記載された物件の事実・条件・注意事項をできるだけ残す。追加項目数は固定しない。未記載事項は推測しない。情報源・確認時点・ユーザー修正の区別は後工程で具体化。
- 掲載元URLを保持し、掲載サイトの写真・掲載内容へ移動できるようにする。写真の全面複製や掲載リンクの永続利用は前提にしない。
- 住所（記載された範囲のみ）、建物名、部屋番号を保持可能にする。Googleマップの住所検索へのリンクを表示し、未確認の位置を正確なピンと誤認させない。
- 基本項目を先に表示し、その他の情報は展開可能にする。読み取り内容はユーザーが確認・修正する。
### C｜内見状況と本人の判断を残す
- 内見前／内見済みのステータスを最初に選び、その状況に合う内容に切り替える。
- 内見前：予定なし／仮予定／予約済み、任意の予定日・予定時刻を記録。変更・中止できる。
- 内見後：実際の内見日・時刻（分かる範囲）、感じたことを記録可能。2回以上の内見にも対応できる履歴を想定。
- 確認ポイントは現在の判断と同じ画面に表示。内見前は「この物件を内見する際のポイント」、内見後は振り返りのヒント。朝・昼・夕・夜の時間帯に応じたヒントを提供するが、季節・方角・天候などの事実を推測して断定しない。
- 内見前の判断例：内見に進みたい／保留したい／今回は見送る。内見後の判断例：引き続き検討したい／保留したい／今回は見送る。正式な判断Stateへの対応は実装前に照合する。
- 「判断を代表する理由を1つ必須で選ぶ」工程は廃止する方向で合意。良い点・気になる点の任意複数タグを選べる。0件でも判断保存可とする方向。自由記述は別途検討可能。
- 物件そのものの下書き保存と、現在の判断の正式保存は別の概念にする。情報不足でも下書きを残せるようにする。正式判断の材料要件は既存Authorityとの限定的な整合確認が必要。
### D｜保存結果と次の行動
- 保存できた物件・内見状況・本人の判断・タグを明示。保存失敗時は成功表示しない。
- 内見に進む人には内見の準備、保留中の人には比較や再検討、見送りの人には次の物件登録など、その判断に関連する実行可能な次の操作を提示。推奨・ランキング・AI購入判断ではない。
- 保存した物件の一覧へ戻れる。後日、同じ物件の内見情報・判断を追加・更新できる。

## 3. Edge/Resume Contracts（UX）
- URL読取不可：入力URLを保持、画像・PDF・手入力への代替導線を提示。
- AIからの復帰：同じ物件の取り込み段階へ復帰し、出力貼付を促す。新しい入力を強制しない。
- タブ切替、ブラウザ再読込、途中離脱：下書き再開を可能にする。保存領域・保存期間・機密情報の扱いは技術設計で決定。
- 情報不足：未記載を推測しない。少なくとも物件下書きは残せるようにする。
- 判断保留：物件だけ保存して終了可能とする。
- 保存エラー：入力保持・再試行を提供。重複保存や誤表示を防ぐ。
- 日程変更／キャンセル：予定を更新し、誤通知を送らない。
- 内見済みの再訪問：内見後の入力・履歴から継続。
- 同じ物件の複数回内見：日時ごとの観察と判断を別イベントとして保持する方向。
- 掲載ページの削除：過去に保存した情報・判断を失わない。

## 4. Data Concepts（物理DB設計ではない）
1. 物件プロフィール：名称、基本9項目、追加の記載情報、住所、掲載URL、情報源。
2. 内見イベント：予定（未定・仮予定・予約済み・変更・中止）、実施日時、複数回の訪問記録。
3. USERの判断：内見前／内見後、本人の選択、任意の複数タグ、時点別履歴。最新判断と履歴は別管理。
4. 復帰・下書き状態：入力途中、データ確認、判断作成、保存完了の区別。
5. LINE通知候補：内見後の記録を促す任意の通知。配信同意、LINE公式アカウントとの接続、対象物件への復帰、変更・中止時の通知停止が前提。通知実装はMVP本体から独立した後続判断。

## 6. Execution/Authority Boundaries
- 本文は「理想UXと現コードを比較するための基準」であり、既存Formal Product Authorityの自動上書きではない。
- とくに代表理由必須の廃止、物件独立保存、任意タグ、内見履歴の扱いは、既存の正式Product DesignおよびSystem/Persistence権限と限定的に整合を取る。
- KEEP/MODIFY/ADD/REMOVEは候補。改修・再実装・不要ページ削除は、依存関係・安全性・総工数を確認して決定。
- すべての実装はMobile First、390×844、モバイルChromeを主対象とする。外部AIのタブ／アプリ切替・復帰を実機で検証する。
- Development M2 Recovery：HOLD/PRESERVED。Production：未承認Mutation禁止。公開前バックアップ・復元・認証・ユーザー間データ隔離等は独立の必須安全確認として保持。
- このチェックポイントの作成でGit、DB、Production、正式設計ファイルには一切Mutationを行っていない。
